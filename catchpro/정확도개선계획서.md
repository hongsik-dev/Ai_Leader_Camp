# CatchPro 정확도 개선 계획서

## 현재 상태

2026-04-24 기준으로 1차 자동오더의 `리스트 화면 OCR -> 후보 행 열기` 구조는 사용하지 않습니다.
인성 리스트에서 오더를 여는 동작은 사용자가 직접 수행하고, CatchPro는 열린 `오더 상세 화면`의 도착지 / 상차거리 / 요금만 기준으로 판정합니다.

아래 계획 중 `동/읍/면 데이터 확장`과 `정식 행정구역 경로 비교`는 반영됐고, `리스트 OCR 후보 탐색` 관련 항목은 과거 검토 내용으로 남겨둔 기록입니다.

## 1. 왜 이 계획이 필요한가

과거 1차 자동오더는 `리스트 화면 OCR -> 후보 행 열기 -> 상세 화면 확인` 구조로 동작했습니다.

이 구조는 속도는 확보할 수 있지만, 아래 문제가 남아 있습니다.

1. OCR이 `도착지 / 상차거리 / 요금` 컬럼을 섞어 읽을 수 있음
2. `구 단위` 또는 `시 단위` 문자열만으로 조건을 비교하면 전국에 같은 이름이 많아 오탐이 생길 수 있음
3. `동` 이름이 같은 지역이 전국에 여러 군데 있어, 현재처럼 축약된 문자열 비교만으로는 잘못된 도착지가 통과할 수 있음
4. 사용자는 `서울 > 강남구`를 골랐을 때, 실제로는 `서울 강남구 역삼동`, `서울 강남구 논현동`처럼 하위 행정구역까지 포함해서 명확하게 보고 싶음

즉 현재 문제의 본질은 `속도`보다 `행정구역 데이터가 너무 거칠다`는 점입니다.

---

## 2. 목표

이번 정확도 개선의 목표는 아래 3가지입니다.

1. `전국 시/도 -> 시/군/구 -> 동/읍/면` 단위까지 명확하게 선택할 수 있게 만들기
2. 자동오더 판단을 `부분 문자열`이 아니라 `정규화된 행정구역 경로` 기준으로 비교하기
3. OCR은 `후보 탐색`에만 쓰고, 최종 확정은 `상세 화면 재검증`을 통과한 경우에만 허용하기

## 3. 핵심 방향

### 방향 A. 목적지 데이터는 구 단위가 아니라 동 단위까지 내려간다

예:

- 현재: `서울 강남구`
- 개선 후:
  - `서울특별시 강남구 역삼동`
  - `서울특별시 강남구 논현동`
  - `서울특별시 강남구 삼성동`

즉 `서울 > 강남구`를 누르면 아래에 포함되는 동 목록이 보여야 합니다.

### 방향 B. 저장되는 값도 풀 경로로 저장한다

단순히 `강남구`만 저장하면 안 되고, 최소한 아래 형태로 저장해야 합니다.

- `서울특별시 강남구`
- `서울특별시 강남구 역삼동`
- `경기도 성남시 분당구 정자동`

가능하면 나중에는 코드도 함께 저장하는 것이 좋습니다.

- 시/도 코드
- 시/군/구 코드
- 법정동 또는 행정동 코드

### 방향 C. 동일 이름 충돌은 상위 행정구역까지 같이 본다

예를 들면:

- `중구`
- `서구`
- `정자동`
- `신촌동`

이런 이름은 여러 지역에 중복될 수 있습니다.

그래서 매칭 규칙은 아래처럼 가야 합니다.

1. `동`만 같다고 통과시키지 않음
2. 최소한 `시/군/구 + 동`이 같이 맞아야 함
3. 가능하면 `시/도 + 시/군/구 + 동` 전체 경로가 맞아야 통과

## 4. 개선 구조

### 4-1. 전국 지역 선택 UI 개선

현재:

- `시/도 선택`
- `시/군/구 선택`

개선 후:

1. `시/도 선택`
2. `시/군/구 선택`
3. `동/읍/면 선택`
4. 최종 선택 결과를 풀 경로로 보여주기

예:

- 서울특별시 강남구 역삼동
- 서울특별시 강남구 논현동
- 경기도 성남시 분당구 정자동

추가 요구:

- `초기화`는 전체 선택값을 전부 비워야 함
- 현재 어떤 지역이 선택되었는지 다이얼로그 안에서 명확히 보여야 함
- `선택된 행정구역 요약`을 화면 카드에도 보여줘야 함

### 4-2. 조건 저장 방식 개선

현재:

- 줄바꿈 문자열 중심

개선 후:

- 내부적으로는 `구조화된 선택값 목록`을 저장
- UI에서는 사람이 읽기 쉬운 요약 문자열을 보여줌

예시 내부 저장:

- province=`서울특별시`
- cityDistrict=`강남구`
- town=`역삼동`

또는

- `서울특별시|강남구|역삼동`

### 4-3. 1차 자동오더 판단 구조 개선

현재:

- 리스트 OCR 결과를 행 단위 후보로 만들고
- 도착지 문자열이 조건과 맞으면 상세 진입

개선 후:

1. 리스트 OCR은 `후보 찾기`만 담당
2. 후보의 도착지 텍스트는 임시값으로만 사용
3. 상세 화면이 열리면 실제 도착지/요금/상차거리를 다시 읽음
4. 저장된 행정구역 데이터와 `정확 경로 비교`를 수행
5. 그때만 팝업 또는 자동확정 허용

즉:

- 리스트 = 빠른 탐색
- 상세 = 최종 판단

### 4-4. 2차 추가오더 판단 구조 개선

2차 자동오더도 같은 원칙으로 갑니다.

1. 메인 오더 목적지도 풀 경로 행정구역으로 정규화
2. 추가 오더 도착지도 상세 화면에서 풀 경로 정규화
3. 같은 방향 / 반경 조건 계산 전에 행정구역 정합성부터 맞는지 확인

## 5. 데이터 설계 제안

### 5-1. 앱에 전국 행정구역 데이터를 번들로 포함

필요 데이터:

- 시/도
- 시/군/구
- 읍/면/동
- 상위 관계
- 표시명
- 정규화용 이름

예시:

```text
서울특별시
 └─ 강남구
    ├─ 역삼동
    ├─ 논현동
    ├─ 삼성동
    └─ 청담동
```

### 5-2. 가능하면 법정동 코드 또는 표준 코드도 같이 사용

문자열만 비교하면 여전히 오차가 남을 수 있으므로, 가능하면 아래 형태가 가장 좋습니다.

- `provinceName`
- `districtName`
- `townName`
- `townCode`

문자열 표시는 사람이 읽게 하고,
실제 비교는 코드 또는 정규화 경로 중심으로 합니다.

---

## 6. 매칭 규칙 제안

### 6-1. 1차 자동오더 도착지 매칭

우선순위:

1. `시/도 + 시/군/구 + 동` 완전 매칭
2. `시/도 + 시/군/구` 매칭
3. `동`만 같은 경우는 통과 금지

예:

- 선택값: `서울특별시 강남구 역삼동`
- 상세 도착지: `서울 강남구 역삼동 123-1`
  - 통과
- 상세 도착지: `서울 강남구 논현동`
  - 불일치
- 상세 도착지: `성남시 분당구 정자동`
  - 불일치
- 상세 도착지: `다른 지역의 역삼동`
  - 불일치

### 6-2. OCR 후보 신뢰도 규칙

리스트 OCR에서 아래 상태면 최종 판단 금지:

- 도착지 텍스트가 너무 짧음
- 숫자/시간/특수문자와 섞여 있음
- 가격 또는 거리 컬럼이 비정상적으로 합쳐짐
- `전체 설정`, `1/1` 같은 UI 문자열이 섞여 있음

이 경우:

- 후보는 열어볼 수는 있지만
- 상세 화면 재검증 전에는 팝업/자동확정 금지

### 6-3. 수동 확인 팝업 기준

수동 확인 팝업에도 아래를 같이 보여줘야 합니다.

- OCR 후보 도착지
- 상세 화면 도착지
- 최종 정규화 결과
- 어떤 조건이 맞았는지

그러면 사용자가 왜 팝업이 떴는지 이해하기 쉬워집니다.

## 7. UI 개편 제안

### 7-1. 1차 자동오더 탭

추가할 것:

- `전국 지역 선택`
- `선택된 시/군/구/동 목록`
- `전체 삭제`
- `구 단위 선택 / 동 단위 선택` 구분

추천 UI:

- 시/도 목록
- 시/군/구 목록
- 동/읍/면 목록
- 하단 `확인 / 전체 초기화 / 취소`
- 상단에 현재 선택 경로 표시

### 7-2. 오더 조건 탭

2차 자동오더는 현재처럼 단순하게 유지하되,
메인 오더 목적지의 정규화 결과를 같이 보여주는 것이 좋습니다.

예:

- 현재 메인 오더 목적지
  - 원문: `강남구 역삼동 123-1`
  - 정규화: `서울특별시 강남구 역삼동`

## 8. 구현 단계

### 1단계. 데이터 구조 교체

- 전국 행정구역 데이터를 `동/읍/면`까지 확장
- 기존 `시/도 + 시/군/구` 구조를 하위 단계 포함 구조로 변경

### 2단계. UI 확장

- 전국 선택 다이얼로그를 3단계 구조로 변경
- 선택된 동 목록을 화면에 노출
- 전체 초기화 / 일부 해제 지원

### 3단계. 저장 포맷 교체

- 문자열 저장 -> 구조화된 경로 저장
- 기존 설정값 마이그레이션 필요

### 4단계. 매칭 엔진 교체

- 문자열 포함 검색 중심에서
- 행정구역 경로 기반 매칭으로 전환

### 5단계. 상세 재검증 강화

- 리스트 OCR 후보와 상세 화면의 불일치 시 확정 금지
- 불일치 이유를 로그와 팝업에 표시

### 6단계. 로그 및 디버그 도구 강화

- 어떤 후보가 왜 걸러졌는지 기록
- 원문 주소 / 정규화 주소 / 최종 판정 결과 저장

## 9. 내가 권장하는 우선순위

지금 가장 효과가 큰 순서는 아래입니다.

1. `전국 행정구역 데이터를 동 단위까지 확장`
2. `전국 선택 UI를 시/군/구/동 3단계로 개편`
3. `도착지 매칭을 행정구역 경로 비교 방식으로 교체`
4. `리스트 OCR은 후보 탐색만, 최종 판단은 상세 재검증만`

즉 제 의견도 사용자 의견과 같습니다.

핵심은:

- `강남구`만 저장하는 게 아니라
- `서울특별시 강남구 역삼동`처럼 더 명확한 데이터를 선택하고
- 그 데이터를 기준으로 비교해야 정확도가 올라갑니다.

---

## 10. 결론

현재 문제는 단순히 OCR 성능만의 문제가 아닙니다.

더 큰 문제는:

- 선택 데이터가 너무 거칠고
- 비교 규칙이 너무 넓다는 점입니다.

그래서 정확도를 올리려면
`OCR 개선`보다 먼저
`전국 행정구역 데이터의 세분화 + 저장 방식 개선 + 상세 재검증 강화`
가 먼저 들어가야 합니다.

다음 구현은 이 계획서 기준으로 아래 순서로 진행하는 것이 가장 좋습니다.

1. 전국 행정구역 데이터 확장
2. 전국 선택 화면 3단계 개편
3. 도착지 매칭 엔진 교체
4. 로그와 팝업에 정규화 결과 표시

---

## 현재 반영한 1차 개선

이번 단계에서는 아래 내용을 먼저 반영했습니다.

1. `서울 강남구` 같은 축약형 대신 `서울특별시 강남구` 같은 풀 경로를 내부 기준으로 사용
2. 예전에 저장된 `서울 강남구`, `경기 수원시` 같은 값도 새 기준으로 자동 변환해서 읽기
3. 전국 선택 화면과 1차 자동오더 화면에서 `서울특별시 강남구 전체`처럼 더 명확한 권역 문구 표시
4. 도착지 비교 시 `시/도 + 시/군/구`가 같이 보일 때만 행정구역 매칭으로 인정하도록 규칙 강화

즉 아직 `동/읍/면` 전체 원본 데이터까지 앱 안에 넣은 상태는 아니지만,
기존보다 훨씬 보수적인 `정식 행정구역 경로 기반` 비교로 한 단계 올려둔 상태입니다.
