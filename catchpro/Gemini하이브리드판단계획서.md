# CatchPro Gemini 하이브리드 판단 계획서

## 현재 상태

2026-04-24 기준으로 리스트 OCR 후보 탐색은 비활성화했습니다.
Gemini 보조 판정은 인성 `오더 상세 화면`에서 주소가 짧거나 보조 문구가 섞여 애매할 때만 사용하는 방향입니다.

## 1. 왜 이 계획이 필요한가

현재 CatchPro의 1차 자동오더는 크게 아래 흐름으로 동작합니다.

1. 사용자가 인성 리스트에서 오더 상세 진입
2. CatchPro가 상세 화면의 도착지 / 요금 / 상차지 거리 확인
3. 조건이 맞으면 팝업 또는 자동확정

문제는 아래와 같습니다.

- 리스트 OCR은 빠르지만 컬럼이 섞이거나 잘못된 행을 열 수 있음
- 상세 화면도 주소가 축약되거나 보조 문구가 섞이면 해석이 흔들릴 수 있음
- 전국에 같은 `구`, `동` 이름이 많아서 문자열 비교만으로는 오탐이 남을 수 있음

즉 지금 필요한 것은 `AI가 전부 판단`하는 구조가 아니라,
`기존 규칙식이 애매한 경우만 AI가 보조`하는 구조입니다.

---

## 2. 목표

이번 계획의 목표는 아래 4가지입니다.

1. 자동오더의 정확도를 높인다
2. 잘못된 도착지나 잘못 열린 상세 화면으로 인한 오탐을 줄인다
3. 속도 손실을 최소화한다
4. AI를 붙이더라도 최종 자동확정은 여전히 예측 가능하게 유지한다

---

## 3. 핵심 방향

### 방향 A. Gemini는 메인 판정기가 아니라 보조 판정기다

Gemini에게 바로 `이 오더 잡아도 되는지`를 전부 맡기지 않습니다.

대신 Gemini는 아래 역할만 담당합니다.

- 주소 정규화
- 출발지 / 도착지 / 적요 구조화
- `하차 도우미`, `상차 작업`, `기사 요청` 같은 노이즈 문구 분리
- 애매한 문자열의 의미 보조 판정

최종 확정 판단은 여전히 CatchPro 로컬 규칙식이 담당합니다.

### 방향 B. 빠른 경로는 로컬 규칙식으로 유지한다

아래 조건이면 Gemini를 호출하지 않습니다.

- 상세 화면 도착지가 명확히 읽힘
- 도착지 / 요금 / 상차거리 조건이 로컬 규칙식으로 확정 가능
- 행정구역 비교 결과가 명확함

즉 명확한 오더는 지금처럼 빠르게 처리하고,
애매한 오더만 Gemini로 넘깁니다.

### 방향 C. Gemini 호출은 애매한 경우에만 제한적으로 한다

아래 같은 경우에만 Gemini를 호출합니다.

- 도착지가 `방이동`, `양재동`처럼 축약되어 있음
- 적요에 주소와 보조 작업 문구가 섞여 있음
- 출발지/도착지 구분이 불명확함
- 전국에 중복되는 동 이름이 있어 상위 행정구역 보강이 필요함

---

## 4. 목표 구조

### 4-1. 1차 자동오더

기본 흐름:

1. 사용자가 인성 오더 리스트에서 상세 화면 진입
2. 상세 화면의 실제 필드 파싱
3. 로컬 규칙식으로 먼저 판단
4. 판단이 애매할 때만 Gemini 보조 판정
5. 최종 결과로 팝업 또는 자동확정

### 4-2. 2차 추가오더

기본 흐름:

1. 메인 오더 목적지를 저장
2. 추가 오더 상세 화면 진입
3. 상차지 거리 / 메인 목적지 반경 계산
4. 도착지 해석이 애매하면 Gemini 보조 판정
5. 최종 결과로 팝업 또는 자동확정

---

## 5. Gemini가 맡는 구체 역할

### 5-1. 주소 정규화

예:

- 입력: `방이동`
- 출력: `서울특별시 송파구 방이동`

- 입력: `수원정자동`
- 출력: `경기도 수원시 장안구 정자동`

- 입력: `양재동`
- 출력: `서울특별시 서초구 양재동`

### 5-2. 필드 구조화

예:

- 입력 텍스트:
  - `출발지: 방이동`
  - `도착지: 안산`
  - `적요: 하차 도우미`

- Gemini 출력:
  - `origin = 서울특별시 송파구 방이동`
  - `destination = 경기도 안산시 ...`
  - `helperTask = true`
  - `helperText = 하차 도우미`

### 5-3. 노이즈 분리

예:

- `하차 도우미`
- `상차 작업`
- `기사 수작업`
- `사다리 필요`

이런 문구는 위치가 아니라 부가 작업 조건입니다.
Gemini는 이를 주소 후보에서 제외하도록 분류합니다.

---

## 6. Gemini 호출 조건 제안

아래 중 하나에 해당하면 Gemini를 호출합니다.

1. 도착지 텍스트 길이가 너무 짧음
   - 예: `방이동`
   - 예: `정자동`

2. 도착지에 상위 행정구역이 없음
   - 예: `송파구 방이동`은 있으나 `서울특별시`가 없음

3. 적요상세와 도착지 텍스트가 충돌함
   - 예: 도착지 후보는 `방이동`, 적요는 `하차 도우미`

4. 출발지와 도착지가 혼동될 가능성이 있음
   - 예: `방이동 -> 안산`
   - 사용자 조건은 `송파구 전체`

5. 전국 선택 지역과 후보 주소가 문자열로만은 정확히 비교되지 않음

---

## 7. Gemini에 보내는 입력 제안

Gemini에 화면 전체를 무조건 보내지 말고, 필요한 최소 정보만 보냅니다.

보낼 정보 예시:

```json
{
  "screenMode": "detail",
  "originText": "방이동",
  "destinationText": "안산",
  "detailNote": "하차 도우미",
  "priceText": "28,000원",
  "pickupDistanceText": "0.8km",
  "selectedRegions": [
    "서울특별시 송파구 전체"
  ]
}
```

즉 민감도와 비용을 줄이기 위해,
스크린샷 원본보다 `이미 추출된 텍스트`를 먼저 보내는 방향이 좋습니다.

---

## 8. Gemini의 출력 형식 제안

Gemini는 설명문이 아니라 반드시 구조화된 JSON만 반환하게 합니다.

예시:

```json
{
  "resolvedOrigin": "서울특별시 송파구 방이동",
  "resolvedDestination": "경기도 안산시 단원구 ...",
  "helperTask": true,
  "confidence": 0.91,
  "reason": "도착지는 안산으로 보이며, 방이동은 출발지입니다."
}
```

CatchPro는 이 JSON만 읽고 후처리합니다.

---

## 9. 최종 판단 규칙

### 9-1. 자동확정 허용 조건

자동확정은 아래를 모두 만족할 때만 허용합니다.

1. 상세 화면 실제 값이 존재함
2. Gemini가 높은 신뢰도로 주소를 정규화함
3. 정규화된 도착지가 사용자가 선택한 행정구역과 일치함
4. 요금 / 상차거리 조건도 만족함
5. 보조 작업 문구가 있더라도 도착지 판정과 충돌하지 않음

### 9-2. 수동 확인 강제 조건

아래는 무조건 수동 확인으로 돌립니다.

1. Gemini 신뢰도가 낮음
2. 출발지와 도착지가 비슷한 텍스트로 충돌
3. 동일한 동 이름이 여러 지역에 걸쳐 있음
4. 도우미 / 사다리 / 특수 작업이 적요에 강하게 포함됨

### 9-3. 무시 조건

아래는 아예 잡지 않습니다.

1. Gemini도 도착지를 명확히 못 정함
2. 도착지보다 출발지가 조건에 더 강하게 맞음
3. 행정구역 비교가 불명확함

---

## 10. 속도 전략

Gemini를 붙이면 속도가 느려질 수 있으므로 아래 전략이 필요합니다.

1. 로컬 규칙식 우선
2. 애매한 경우에만 Gemini 호출
3. 같은 주소 표현은 캐시 사용
4. 같은 오더를 반복 호출하지 않기
5. 상세 화면 기준으로만 호출

즉 모든 오더를 Gemini로 보내는 방식은 피해야 합니다.

---

## 11. 구현 단계 제안

### 1단계. 보조 판정 인터페이스 추가

- `AiOrderResolutionService` 인터페이스 정의
- 현재는 mock 구현으로 먼저 연결
- 응답 형식은 JSON 구조로 고정

### 2단계. 애매한 상세 화면만 AI 호출

- 상세 화면 파싱 결과에 `ambiguous = true/false` 추가
- ambiguous인 경우만 Gemini 호출

### 3단계. 주소 정규화 캐시 추가

- `양재동`, `방이동`, `정자동` 같은 반복 주소 캐시
- 같은 주소는 재호출 최소화

### 4단계. 수동 확인과 연결

- Gemini가 보조 판정한 경우 팝업에
  - 정규화된 도착지
  - 보조 이유
  - 신뢰도
  표시

### 5단계. 자동확정 허용 범위 확대

- 충분히 안정화된 뒤에만
  - `고신뢰도 + 조건 일치`인 경우 자동확정 허용

---

## 12. 예상 장점

- `방이동` 같은 축약 주소 해석 강화
- `하차 도우미` 같은 노이즈 분리 강화
- 출발지/도착지 혼동 감소
- 전국 중복 동 이름 문제 완화

---

## 13. 예상 단점과 주의점

- 응답 지연이 생길 수 있음
- 외부 API 호출 비용이 있음
- 네트워크 불안정 시 판단이 늦어질 수 있음
- 인성 데이터 텍스트를 외부로 보내는 정책 검토가 필요함

---

## 14. 최종 권고

가장 추천하는 방향은 아래입니다.

1. `리스트 자동탭`은 사용하지 않음
2. 사용자가 연 `상세 화면`에서 로컬 규칙식으로 먼저 판단
3. 로컬로 명확하지 않은 경우에만 Gemini 보조 판정
4. 초기에는 Gemini 결과를 `수동 확인 보조`로만 사용
5. 충분히 안정화된 뒤에만 자동확정 범위를 일부 확대

즉 `Gemini 단독 자동오더`보다는
`규칙식 + Gemini 보조판정`이 CatchPro 목적에 가장 잘 맞습니다.
